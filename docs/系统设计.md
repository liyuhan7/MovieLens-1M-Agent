## 1. 系统概览

用户在简易前端用自然语言提出数据治理需求。Agent 理解目标后调用工具完成：原始数据质量评估
（五维评分）→ Hadoop 清洗 → 清洗后质量评估 → 证据与结果汇总 → 正式发布与回答。

```text
用户请求
  ↓
Agent 理解治理目标（LLM，工具调用）
  ↓
创建 Logical Run ── 固定输入版本 / 规则版本 / 指标版本 / 执行身份
  ↓
原始数据质量评估 → 数据清洗 → 清洗后质量评估
  ↓
产物校验（Parquet 清洗数据、隔离记录、质量明细、Evidence、Manifest）
  ↓
唯一发布 → 正式结果与报告 → 查询 / 历史比较 / 证据 / Hive 分析
```

系统同时支持两种执行形态，共用同一套规则、指标、元数据与发布语义：

| 形态 | 计算执行 | 存储 | 适用场景 |
| --- | --- | --- | --- |
| local 适配 | 容器内 Hadoop local MapReduce | 本地文件系统 | 单机开发与快速回归 |
| 治理形态 | 单节点 HDFS + YARN（`dfs.replication=1`） | HDFS + MySQL | 需要持久任务、正式发布与历史查询 |

两种形态都不构成多节点分布式集群，不证明跨物理机器容错或高可用。

## 2. 分层与职责

### 2.1 模块边界

| 层 | 职责 | 代码位置 |
| --- | --- | --- |
| 接入层 | 自然语言请求、HTTP 参数与错误适配、会话与追问 | `agent/loop.py`、`agent/server.py`、`web/` |
| 运行控制 | Run 提交、幂等控制、状态迁移、持久队列、租约与恢复 | `governance/service.py`、`governance/worker.py`、`metadata/` |
| 计算 | MapReduce 清洗与评分、作业标识与恢复 | `hadoop/src/main/java/mliter1/`、`pipeline/` |
| 产物与证据 | Parquet 导出、来源协议、质量明细、Evidence Index、Manifest | `governance/artifacts.py`、`governance/indexing.py`、`governance/provenance.py` |
| 校验与发布 | 内容门禁、唯一发布协议、中断恢复、存储对账 | `governance/validation.py`、`governance/publication.py`、`governance/reconciliation.py` |
| 结果服务 | 正式结果/证据查询、历史列表与版本比较、Hive 投影 | `agent/results.py`、`agent/published.py`、`governance/history.py` |
| 观测与运维 | 性能基线、语义等价、保留预览、备份恢复、维护切换 | `governance/performance.py`、`governance/equivalence.py`、`governance/maintenance.py`、`governance/backup.py` |

模块边界在单一应用内建立，不要求拆成多套网络服务。Agent 只通过业务服务提交与查询，
不直接读写业务状态。

### 2.2 组件职责

| 组件 | 职责 | 主要读取方 | 约束 |
| --- | --- | --- | --- |
| HDFS | Raw、Quarantine、Staging、Cleaned、Quality Detail、Evidence、Published Report 本体 | Hadoop、结果服务、Hive | Raw 与正式产物不可被普通重试覆盖 |
| MySQL | Dataset/Version、Rule/Metric、Run/Attempt、Job 关联、Quality Summary、Publish、Evidence Index | 运行控制、结果服务 | 唯一业务元数据权威库；不把数据正文与完整日志全部入库 |
| MapReduce + YARN | 清洗、评分与证据生成；作业调度与执行状态 | 运行控制 | 实际状态结合 YARN、ApplicationMaster/JobHistory 核对；计算成功仍须业务校验 |
| Parquet | 正式结构化清洗数据、隔离记录、质量明细与证据 | Hadoop、Hive、结果服务 | 明确 Schema、编码与空值；原始 `.dat` 保留原样 |
| Hive External Table | 已发布数据的批量 SQL 与历史分析 | 历史分析接口 | 不承担前端高频轮询，不另造权威数据副本 |
| HDFS/Parquet + MySQL Evidence Index | 保存证据正文，按 Run/Rule/Metric/Source Record 定位 | 报告、Agent、结果服务 | 索引与正文可对账；样例不能替代足够的正式证据 |
| Attempt 暂存 + MySQL 唯一发布 | 隔离重试输出，校验并控制正式可见性 | 运行控制、结果服务 | 同一 Run 最多一个正式发布；MySQL 与 HDFS 一致性靠恢复与对账维护 |

### 2.3 部署形态

单机开发环境为 Windows Docker Desktop 中的 Linux 容器：一个 Hadoop 容器内的
NameNode、DataNode、ResourceManager、NodeManager、JobHistoryServer，另设 MySQL 与
Linux worker 容器。数据库、HDFS 与历史日志使用持久卷；端口、资源与路径由配置管理。

单机验证从一个 DataNode/NodeManager 开始，用于验证真实 HDFS 读写与 YARN 执行。
Hadoop 固定 3.3.6，采用官方单节点 HDFS/YARN 配置；多节点与 HA 在需要时追加。
环境准备、端口与验证分层见 [runtime/README.md](../runtime/README.md)。

## 3. 数据区与目录约定

```text
/movielens/raw/dataset_version=<input_version>/
/movielens/staging/run_id=<run_id>/attempt_id=<attempt_id>/
    jobs/<stage>/
    cleaned/<table>/
    quarantine/<table>/
    quality/
    evidence/
    report.json
    manifest.json
/movielens/cleaned/dataset_version=<output_version>/<table>/
/movielens/quarantine/run_id=<run_id>/
/movielens/quality/run_id=<run_id>/
/movielens/evidence/run_id=<run_id>/
/movielens/published/run_id=<run_id>/report.json、manifest.json
```

同一 Attempt 的全部中间、隔离与证据输出先在其 Staging 内形成，失败尝试不写入正式数据区。
Evidence 目录按 Run 组织，但不为每个 Run/Evidence ID 建立 Hive 分区。

结构化 Schema 至少保留：

- **users**：用户 ID、可空性别/年龄段/职业、字符串邮编；真实缺失使用 null，邮编保留前导零。
- **movies**：电影 ID、标题、可空年份与完整类型集合；类型使用字符串数组并验证 Hive 兼容性。
- **ratings**：用户 ID、电影 ID、整数评分、秒级 UTC 时间戳；评分值域与 T1/T2 维持已登记口径。
- **Quarantine**：源记录标识、原始记录、规则、原因与最终处置；原始字节或可复原引用随输入版本保留。
- **Evidence**：源表/文件/偏移、Finding、规则版本、动作、前后值或校验值、指标、Run/Attempt 与结果引用。

原始输入保持 Latin-1 字节，计算输出为 UTF-8；编码转换记录在版本与文件清单中。
正式目录位置由发布元数据与 Manifest 定位，文件系统路径本身不是权威。

## 4. 数据与版本身份

系统有四条独立版本轴，正式结果不可由 `latest` 或完成时间决定。

### 4.1 输入数据版本

输入指纹由三表文件内容派生为 `dataset_version`，登记完整 SHA-256、文件清单、Schema 与
可用状态。内容指纹独立于创建日期：只改导入时间不改变事实输入，内容变化则产生新版本。
已登记版本不可原地替换。

### 4.2 规则版本与指标版本

规则版本（`rules-v2.0`）与指标版本（`metrics-v2.1`）分别登记定义与内容校验值。
已被正式结果引用的定义不可改写；含义变化时发布新版本，并明确历史不可直接比较的部分。
指标契约存放于 `schemas/`，运行时按版本加载。

### 4.3 输出数据版本与 Manifest

每次正式发布产生新的 `output_data_version`，Manifest 固定该版本的完整文件清单、
Schema、编码、行数与 SHA-256。报告由指标与 Evidence 确定性生成；前端样例由正式产物派生，
不作为唯一证据。

## 5. 元数据模型

MySQL 是业务元数据权威库，核心关系如下：

| 对象 | 关键记录 | 核心约束 |
| --- | --- | --- |
| `dataset` / `dataset_version` | 数据集、父版本、三表位置与完整 SHA-256、Schema/编码、Manifest、可用状态 | 已登记版本不可原地替换；内容指纹独立于创建日期 |
| `rule_version` / `metric_version` | 规则定义、评分公式、权重、T1/T2 配置引用及内容校验值 | 被正式结果引用的定义不可改写 |
| `logical_run` | Run ID、幂等键、输入/规则/指标版本、阶段、状态、请求参数指纹、提交序号、失败原因 | 幂等键在规定作用域内唯一；同键不同参数拒绝 |
| `physical_attempt` | Attempt ID、Run ID、序号、工作路径、状态、租约、开始与结束时间 | `UNIQUE(run_id, attempt_no)`；过期执行者不能修改新尝试状态或发布结果 |
| `hadoop_job` | Attempt、阶段、提交关联标识、Job ID、Application ID、状态摘要、日志位置 | 一个 Attempt 关联多个阶段 Job；框架 Task Attempt 与业务 Attempt 分开记录 |
| `quality_result` | Run/Attempt、before/after、表、维度、分子分母、得分、指标版本、证据引用 | 候选结果按 Attempt 隔离；对外正式摘要只关联胜出的 Publish |
| `evidence_index` | Evidence ID、Run/Attempt、源记录、规则/指标、文件与文件内定位信息 | 正文与索引一致；相同批次重入不重复登记 |
| `publish_version` / `dataset_current` | Run、胜出 Attempt、输出版本、Manifest、报告、发布状态、当前指针 | `UNIQUE(run_id)` 保证同一 Run 最多一个正式发布；current 使用并发条件检查 |

同时保存报告 Schema 版本、执行代码/构建版本、jar 校验值、镜像摘要、Agent 模型与 Prompt
版本，使历史报告能够还原所用规则与执行条件。对话 SQLite 保留，但不决定业务任务状态。
Hive Metastore 使用独立库与账号，查询层元数据不混入治理业务表。

索引覆盖：Run ID 点查；Dataset + 状态 + 创建时间的历史列表；按输入/规则/指标版本比较；
Run 下的 Attempt/Job；Run + Rule/Metric/Source Record 的证据定位。列表必须分页，
不读取全部历史 JSON 后再筛选。

## 6. 运行生命周期

### 6.1 状态机

```text
ACCEPTED → QUEUED → RUNNING → VALIDATING → PUBLISHING → PUBLISHED
```

已确认的计算或校验失败记为 `FAILED`，保存失败阶段与可重试原因；执行状态暂时无法确认时
进入恢复/待核对状态，不直接判失败。重试保留 `run_id`，创建新 Attempt 并记录重试事件。

治理请求与只读对话严格区分：只读查询绑定已有 Run 或明确选定的 current，不创建假的治理运行。

### 6.2 幂等与重试

幂等键用于识别同一请求的重复送达：同键同参数复用同一 Run，同键不同参数返回冲突。
相同数据上的一次明确重跑使用新键形成新 Run。报告复用必须比较完整输入、规则与指标条件，
不依赖模型判断“数据好像没变”。

### 6.3 持久队列、租约与执行令牌

采用 MySQL 持久队列与单 worker，串行执行即可满足低并发场景。worker 获取任务后持有
可恢复的租约与执行令牌；租约过期的旧执行者不得覆盖新的任务状态或获得发布资格。

提交外部作业前先保存阶段与关联标识，提交后尽快保存 Job/Application ID。针对
“Job 已提交但确认信息未入库”的窗口，通过可检索的提交关联标识、作业名称/标签与日志
定位已有执行；无法确认时保持待核对，避免盲目重复提交。

### 6.4 恢复与对账

重启时先对账未完成 Job，再决定恢复或重试。完整性通过的阶段产物可以复用，复用前核对
版本、Manifest 与校验值。跨组件一致性通过只读存储对账维护：以 MySQL 的 `PUBLISHED`
与已核验 Manifest 为准，核对正式 HDFS 文件集合、字节与指纹，识别孤立产物。

## 7. 计算产物与证据

### 7.1 结构化产物

清洗后数据、隔离记录、质量明细与证据统一导出 Parquet，遵守 §3 的 Schema 约定。
Parquet 定位信息（例如 row group）随 Evidence 保存，用于缩小读取范围；不为每条证据
生成一个小文件。

### 7.2 来源协议与动作链

源记录身份为 SHA-256：输入版本、源表、源文件相对路径与原始字节偏移，以零字节分隔后
编码为 UTF-8。单一偏移不能区分多个文件，因此多文件输入不能只靠偏移区分。

中间记录使用四段 envelope，首段为 `offset@base64url(origin_json)`；origin 保存源身份、
原始记录、事件链与合并来源关系。电影第二次去重必须继承它，中间文件偏移不能成为新的
原始来源。事件链中每一步保存 rule、action、before、after，去重事件还指向胜出来源。
记录最终去向与动作次数分别统计，每条原始记录只计一次最终去向。

### 7.3 质量明细与摘要

每个指标保存分子、分母、得分、指标版本与证据引用，按 Attempt 隔离；正式摘要只关联
胜出的 Publish。`Quality Summary` 的分子分母与明细一致，不适用维度保存 null，
公式按指标版本可复算。

### 7.4 Evidence Index

Evidence 正文与索引可对账：结合文件路径、Evidence ID 与文件内定位信息缩小读取范围。
没有来源标识或事件链的历史样例不能补造为正式证据。

## 8. 校验与唯一发布

### 8.1 发布门禁

计算完成先进入 `VALIDATING`。发布前至少验证：

1. 输入数据版本、Rule/Metric 版本与执行构建信息完整，且与本 Run 固定条件一致。
2. 必需的三表输出、隔离数据、质量结果、Evidence、结构化 Report 与 Manifest 都存在。
3. Schema、编码、字段值域与文件校验值通过；全部分区都参与统计。
4. 每张原始表的记录可按最终去向对账：保留、隔离、去重移出的记录各计一次；多阶段电影
   输出与多条动作日志不重复当作原始记录。
5. 清洗后 ratings 的引用有效，`train + valid + test` 等于符合切分条件的最终评分数；
   不适用指标明确标注。
6. Quality Summary 的分子、分母与得分与明细一致；正式结论可定位 Evidence，
   证据版本与来源匹配。
7. 当前 Attempt 拥有有效执行资格，且同一 Run 没有其他已发布结果。

门禁同时检查报告派生字段：重新计算文件 SHA-256 后仍能识别综合分、增量、切分数量/边界、
移除总数等字段的篡改。

### 8.2 可恢复发布协议

```text
Attempt 校验通过
  → MySQL 建立唯一的待发布记录，固定胜出 Attempt 与 Manifest
  → 将已校验产物按固定路径物化到正式区，核对实际文件
  → MySQL 事务确认 Publish、正式摘要与 Run = PUBLISHED
  → 按明确策略申请更新 current
```

文件存在不能直接使结果正式可见；结果服务与 Hive 分区登记以 MySQL 的 `PUBLISHED`
及已核验 Manifest 为准。HDFS 与 MySQL 不具备共同原子事务，因此恢复须处理两类中断：
文件已落地但元数据未确认时，校验同一发布记录并补完；待发布记录已建立但文件未完成时，
继续同一发布过程或标明失败，不新增另一份正式版本。

待发布 Attempt 无法补全而需更换执行结果时，只能在尚未 `PUBLISHED` 时复用同一待发布
记录，重新校验候选产物并记录资格转移；不能改写已发布记录或产生第二份正式版本。
操作者入口为 `runtime/request-publication-replacement.py`：显式 CAS，要求原 Publish、
Attempt、Manifest 校验值与令牌的完整预期及原因，仅在未正式发布、无有效租约且外部作业
均确认终态时排队替代 Attempt。

结构化 Report 缺失时拒绝发布。正式报告与证据完整而 LLM 概述生成失败时，保存独立的
解释失败状态，允许查询正式报告并明确显示“解释未生成”，不伪造自然语言总结。

### 8.3 current 更新

发布与 current 更新分开。current 更新检查预期版本与请求顺序/提升资格；较旧 Run 可以
形成历史正式结果，但不能因晚完成而覆盖更新的 current。指针变更事件保留，
已发布的文件与报告不被普通重试改写。

### 8.4 跨组件对账

`governance/reconciliation.py` 提供只读对账：核对正式引用、孤立产物与缺失材料，
不修改 HDFS 或元数据。正式文件的独立全字节复核由
`tests/verify_published_storage.py --run <run_id>` 完成，核对完整文件集合、每个文件
大小与 SHA-256 以及 SQL Manifest 指纹。

## 9. 查询与解释

### 9.1 正式结果与证据

`GET /api/runs/{run_id}/report`（含 `/report/download`）按 Publish 选择胜出 Attempt，
校验 Manifest 自身、报告字节 SHA-256、大小与完整版本绑定，再返回报告字节及 `X-Publish-ID`：

| 情况 | 响应 |
| --- | --- |
| 未知 Run | 404 |
| 未正式发布 | 409 |
| 缓存缺失 | 按该 Publish 的正式 HDFS 路径取回、校验完整字节并原子创建 |
| 缓存损坏或正式存储不可用 | 503，不覆盖损坏缓存 |

结果选择不回退到其它 Run。按规则、记录、指标与证据身份查询正文走
`GET /api/runs/{run_id}/evidence`，定位正式文件行组并核对正文/索引/版本，
未知范围不切换到别的结果。

### 9.2 历史列表与版本比较

MySQL 提供持久列表与分页，支持按状态、数据集、输入、规则与指标版本筛选；
游标基于请求序号，筛选在参数化 SQL 中完成。`GET /api/datasets/{dataset_id}/current`
返回正式获胜 Attempt 的固定身份，查询开始后该范围不再改变。

版本比较固定两个正式任务，返回评分、版本与行数变化；不同指标版本不计算评分差值，
不同规则版本不计算动作差值。历史分析按同数据集的 2～10 个正式版本返回五维质量、
表/数据集综合分与规则动作汇总，以及相邻版本的 `quality_delta`、
`dataset_composite_delta`、`action_delta`；不适用维度保持 null，描述性差值不归因于单条规则。

### 9.3 Hive 只读外部表

Hive 外部表只登记已发布的 Cleaned、Quality Detail 与 Evidence，共 8 张投影
（3 张 Cleaned、2 张质量阶段、3 张 Evidence），按输出版本分区。登记前核对正式文件
完整清单与字节，检查字段、分区字段、Parquet 格式、防删除属性及正式 HDFS 服务/路径；
查询前再次核对元数据，查询后核对数量与版本身份。外部表采用保留数据的配置并验证
删表后文件与校验值仍存在。不兼容的旧表拒绝使用，不自动修改元数据或正式文件。

### 9.4 Agent 结论引用校验

Agent 提交 `ConclusionProposal`，固定 `run_id`、`publish_id` 与输入/规则/指标版本：

- `report_claims` 使用报告标量字段的 JSON Pointer，字段与值一同核验，不能用其他字段中
  的同一数字代替。
- `evidence_claims` 必须匹配来源记录、数据表、规则、指标、动作、处理前后值与最终处置。
- 校验器从正式证据读取事实，不接受模型给出的任意原因文字作为已证明的因果解释。

响应包含 `accepted_claims`、`rejected_claims`、`validation_status` 与 `hypotheses`。
只有通过校验的事实进入正式答复；推测明确 `hypotheses_verified=false`；无可核验事实时
返回材料不足。旧文本响应保留兼容数字检查，但标记 `UNVERIFIED`，不作为正式结论。

Agent 只读会话绑定首次已校验的正式 Run（SQLite `agent_report_binding`），重复同一绑定
可复用、不允许更换，重启后的追问沿原 Run 查询并保留原会话历史。

## 10. 性能观测与优化

每张表的评分作业在单次扫描内计算多维指标，不拆成“五维各一个 Job”。采集每阶段
输入/输出字节、耗时、Shuffle、Map/Reduce 数量、重试与 Partition 分布，并支持可选的
逐 Task Attempt 明细（重试/推测执行成本、Reduce 阶段耗时、分区记录量/空分区/倾斜比例）。
基线绑定所比较的正式 Attempt 与执行材料，仅同版本可比。

按实测结果优先评估：可复用参照集合、Mapper 局部统计、仅对可结合的计数使用 Combiner、
避免隔离记录全部汇入单个 `ISO` Key、按全部分区聚合以及流式处理大组。不能直接把最终
计算重复超额的 Reducer 当作 Combiner，否则会改变 Unique 语义。

优化前后用 `governance/equivalence.py` 比较业务语义：全量读取 20 项 Parquet 与业务报告
字段，以磁盘 SQLite 比较精确业务行多重集合，并验证每行版本、证据 ID、文件字节、Schema
与行数。结果等价不代表规则本身正确，也不代表已有实测性能收益。

## 11. 保留策略

Raw、Published、正式 Evidence 及其 Manifest 按版本保留；失败/废弃 Attempt 与临时预览
按策略归档或清理。清理工具只输出候选清单，说明路径、原因、保留依据、大小与依赖；
候选保护正式依赖与活动租约，扫描后重新核对元数据，未知对象要求人工复核。
单机副本不能替代备份。

## 12. 备份、恢复与维护切换

**备份**要求 Run 与 Attempt 均已终态、执行槽位空闲、无未完成发布意图。通过一致性事务
读取元数据，Evidence Index 流式导出；复制已登记 Raw、Published 文件与历史报告，
并校验完整 SHA-256、字节长度、清单身份、元数据行数与引用覆盖。未完成的包不写完成清单，
保留诊断材料。

**恢复**只接受已存在的空 `ml_governance_restore_<名称>` 数据库：先校验整个包，准备
当前 Schema，再复制不可变文件，最后在单一 SQL 事务中恢复元数据。目标非空、文件冲突与
版本依赖异常均拒绝；文件失败时没有恢复后的 Run/current 可见。

**维护排空与切换**：接入控制包含维护开关、修订号、维护者与审计事件。排空阻止新的提交、
重试与首次领取，允许在途恢复；排空后切换兼容 API 镜像并记录原镜像，失败保持关闭。
切换预留同时阻止 Worker 领取与新的发布替代授权。操作步骤见
[runtime/DEPLOYMENT.md](../runtime/DEPLOYMENT.md)。

备份包包含元数据与 Raw/Published/历史字节；检查点不包括运行中的作业恢复、失败暂存目录、
对话数据库、原始日志、镜像或密钥。镜像归档与运行环境凭据按部署说明分别保存。

## 13. 历史数据兼容

历史报告（旧 `registry.json` 登记、旧 tag 与报告内部 ID）通过显式映射导入历史档案：

1. 以源路径与完整 SHA-256 派生导入键，重复导入不新增记录。
2. 报告字节经完整校验后登记路径/校验值及源 tag、登记 task_id、报告内部 task_id 的显式映射。
3. 缺少清洗数据或完整证据的历史结果标记为 `LEGACY_INCOMPLETE`，`formal_publication_verified=false`；
   不据旧 `status=success` 建立新正式发布，也不据样例补造 Evidence。
4. 同名冲突返回 409；未知身份/空身份不回退 latest；材料缺失或数据库不可用返回 503。

`GET /api/legacy/reports/{归档ID或显式别名}` 提供历史身份查询；
`registry.json` 保留兼容读取，仅作为兼容导出，不决定正式发布或 current。
基线校验值清单见 [历史报告基线清单.json](历史报告基线清单.json)。

## 15. 已知边界与未验证范围

1. 执行模式是容器内 Hadoop local MapReduce 或**单节点 HDFS/YARN**（`dfs.replication=1`），
   不是多节点分布式集群，不证明跨物理机器容错或高可用。
2. 五维中的 Accurate 评的是值域合规与引用可解析，无法验证真实世界准确性；
   users/movies 无时间字段，Up-to-date 记为“不适用”，不参与综合分。
3. 置 NULL 与登记仍保留记录（登记 ≠ 修复）；隔离会缩小分母，分数上升部分来自剔除劣质记录。
4. `registry.json` 为追加写、不去重；`outputs/_tmp_*` 中间产物可安全删除。
5. Agent 写工具只在用户原话命中“重新/重跑/清洗”类触发词时注入，其余场景只读复用最新报告。
6. 真实 MySQL/HDFS/YARN/Hive 全量规模、性能基线、复杂恢复、跨机器部署与远端 CI 的集中验收
   尚未完成；模块级用例通过不代表上述环境已验收。开发环境依赖本机已有基础镜像，
   跨机器完整重建尚不可复现。
7. 同名电影归并未按“有评分记录的 ID 优先”执行，电影表也未实现设计中的 ID 归并与
   缺失标题补全；实际执行口径已写入报告局限。
